# Pantry Item API

The Pantry Item API manages ingredients stored in a user's pantry.

Each pantry item belongs to one user and contains the ingredient name, available quantity, and measurement unit.

## Data Model

The current `PantryItem` entity contains the following fields:

| Field      | Type     | Description                                           |
| ---------- | -------- | ----------------------------------------------------- |
| `id`       | `Long`   | Unique identifier generated by the database           |
| `name`     | `String` | Name of the pantry ingredient                         |
| `quantity` | `Double` | Amount of the ingredient available                    |
| `unit`     | `String` | Measurement unit, such as `g`, `kg`, `ml`, or `piece` |
| `user`     | `User`   | User who owns the pantry item                         |

## Entity Relationship

The relationship between users and pantry items is:

```text
User 1 ─────── * PantryItem
```

This means:

* One user can have multiple pantry items.
* Each pantry item belongs to one user.

The relationship is represented using JPA:

```java
@ManyToOne
@JoinColumn(name = "user_id")
private User user;
```

The `user_id` column in the `pantry_items` database table references the owner of the pantry item.

## Example Database Records

| id | name           | quantity | unit  | user_id |
| -: | -------------- | -------: | ----- | ------: |
|  1 | Chicken breast |      500 | g     |      10 |
|  2 | Rice           |        2 | kg    |      10 |
|  3 | Tomatoes       |        6 | piece |      25 |

In this example:

* Items `1` and `2` belong to user `10`.
* Item `3` belongs to user `25`.

## Request Example

A client request for creating a pantry item should contain the pantry item information:

```json
{
  "name": "Chicken breast",
  "quantity": 500,
  "unit": "g"
}
```

The client should not normally choose the `userId`. The backend should obtain the current user from the authenticated session or security token and assign that user as the owner.

Conceptually:

```java
pantryItem.setUser(currentUser);
```

## Response Example

A pantry item response may look like:

```json
{
  "id": 1,
  "name": "Chicken breast",
  "quantity": 500,
  "unit": "g"
}
```

The API response should not return the complete `User` entity because it may expose internal account information.

A response DTO should therefore contain only the pantry item fields that the frontend needs.

Example:

```java
public record PantryItemResponse(
    Long id,
    String name,
    Double quantity,
    String unit
) {
}
```

## Suggested Endpoints

### Get the Current User's Pantry

```http
GET /api/pantry
```

Returns all pantry items owned by the authenticated user.

Example response:

```json
[
  {
    "id": 1,
    "name": "Chicken breast",
    "quantity": 500,
    "unit": "g"
  },
  {
    "id": 2,
    "name": "Rice",
    "quantity": 2,
    "unit": "kg"
  }
]
```

### Get One Pantry Item

```http
GET /api/pantry/{id}
```

Returns one pantry item only if it belongs to the authenticated user.

### Create a Pantry Item

```http
POST /api/pantry
```

Example request:

```json
{
  "name": "Olive oil",
  "quantity": 750,
  "unit": "ml"
}
```

Suggested successful response status:

```http
201 Created
```

### Update a Pantry Item

```http
PUT /api/pantry/{id}
```

Example request:

```json
{
  "name": "Olive oil",
  "quantity": 500,
  "unit": "ml"
}
```

The backend should verify that the pantry item belongs to the authenticated user before updating it.

### Delete a Pantry Item

```http
DELETE /api/pantry/{id}
```

Suggested successful response status:

```http
204 No Content
```

The backend should verify ownership before deleting the item.

## Ownership and Security

Pantry data must be isolated by user.

The backend should never load all pantry items globally for a user-specific request. Repository operations should include the authenticated user's ID.

Example repository methods:

```java
List<PantryItem> findAllByUserId(Long userId);

Optional<PantryItem> findByIdAndUserId(
    Long pantryItemId,
    Long userId
);
```

Using both the pantry item ID and user ID prevents one user from accessing or modifying another user's pantry item.

## Validation Rules

Recommended validation rules include:

* `name` must not be blank.
* `quantity` must not be null.
* `quantity` must be greater than zero.
* `unit` must not be blank.
* `user` must not be null.

Example request validation:

```java
@NotBlank
private String name;

@NotNull
@Positive
private Double quantity;

@NotBlank
private String unit;
```

The `user` field should be assigned by the backend rather than accepted directly from the client.

## Current Limitations

The current entity stores the ingredient name as free-form text:

```java
private String name;
```

This means values such as the following may be treated as different ingredients:

```text
Tomato
tomato
Tomatoes
 tomato
```

A future version should introduce a normalized `Ingredient` entity and connect pantry items using an `ingredient_id` foreign key.

The intended relationship would then become:

```text
User 1 ─── * PantryItem * ─── 1 Ingredient
```

This will improve ingredient matching between pantry items, recipes, grocery items, and recommendations.
